# M5 — a CMS with storage above 16 MB (scoped 5 October 2026)

M2 is complete: CP runs AMODE 31, presents 31-bit virtual machines up to
256 MB, and a guest that sets PSW bit 32 stores above the line and takes
interrupts there (G31, `34-AMODE31.md` step 3). CE's CMS gets none of it: it
is a 24-bit, **BC-mode** program. This note measures what stands between the
two and fixes the order of work. The goal is stated the way Mike put it: a CMS
with much more memory, enough to compile cREXX (~18 MB) on this machine.

## What CMS is, architecturally (source/cms, 175 members, 158,715 lines)

| | Count | Where |
|---|---|---|
| BC-mode PSW decoding — ILC and interrupt code read out of the OLD PSW itself (`OPSW+3`, `OPSW+4,X'80'`) | 16 sites | DMSITS 7, DMSITE 4, DMSITP 3, DMSIOW 1, DMSINI 1 |
| PSW constants in BC format (`=AL1(0,MCKM,0,202)`, `X'FF06…'`, wait PSWs) | 9 modules | DMSABN DMSARX DMSASM DMSFNS DMSINI DMSINS DMSIOW DMSITS DMSSVN |
| `LA Rx,0(,Ry)` 24-bit strips (strips.py) | 156 | self 131, copy 25 |
| `ICM Rx,7` three-byte pointer loads | 34 | DMSXCP, DMSROS, DMSLDS, DMSDSV, DMSOPL … |
| `BALR Rx,0` (CC saves vs bases, to classify) | 103 | |
| Storage sizing | DIAG X'60' in DMSINI; `DMSINS` loads the nucleus HIGH, just under the VM size, and treats >16M as "too small" (I-232's `DMSINI260T`) | |
| Free storage | DMSFRE: four chains (low/high × nucleus/user), 24-bit addresses, `count || address` words in CODE203/plists; CE's `kernel-c` STAT increment already reads the chains from C | |
| Application interface | SVC 202/203 with the plist in R1 and **flags in byte 0 of R1** (extended plist X'01', …); FSCBs and PLISTs with 24-bit address fields; DIAG plists with 24-bit addresses (126 DIAG sites) | |

The decisive fact is the first row: **a BC-mode PSW cannot carry bit 32** —
bits 32-33 are the ILC. Nothing above the line is reachable from CMS until
CMS runs in EC mode. That is the first increment, and it is small.

## The design: XA-CMS-light, not a rewrite

IBM answered this once (VM/XA CMS, 1988): keep the nucleus and every
existing interface below 16 MB, run in EC mode, let programs *that ask*
run AMODE 31 and get storage above the line, and bridge the service calls.
Adrian's "private high code and data with low service bridges" is the same
shape. We follow it:

1. **The nucleus stays below 16 MB**, loaded high as today (DMSINS), so
   every existing CMS program, FSCB, PLIST and DIAG keeps working unchanged
   — the 24-bit application world is preserved by construction.
2. **CMS runs in EC mode.** Its own PSWs become EC format; the five
   handlers read ILC/code from the fixed locations (X'84'–X'8F') instead
   of the old PSW. CP supplies the EC machine (the `ECMODE` directory
   option, which MAINT needs anyway).
3. **DMSFRE gets a fifth region: 16 MB to VMSIZE**, handed out only to a
   request that asks (a new DMSFREE/DMSFRET option bit in CODE203, and the
   SVCFREE plist), so no legacy caller ever sees a high address. DMSINS
   stops refusing machines above 16 MB; `DMSFRES STAT` and CMSSTOR report
   the new region.
4. **AMODE 31 programs.** A program switches with `BSM`; `SVC 202/203`
   from AMODE 31 is accepted by DMSITS, which keeps the caller's PSW whole
   (bit 32 and all — it already saves/restores the full old PSW) and reads
   R1's flag byte only when the caller is 24-bit (`TM` on the saved PSW);
   the plist itself must be below the line, as IBM's own rule for calling
   24-bit services says. Return restores the caller's mode (LPSW of the
   saved PSW does).
5. **The C runtime** (GCCLIB/PDPCLIB `memmgr`) asks DMSFREE for the high
   region when built for it; i370-gcc's generated code is base-displacement
   and `BALR`-linked and needs reading for 24-bit assumptions, not
   converting. cREXX compiled with that runtime has its heap above the line
   while its code and CMS stay below.

What this does **not** do: it does not make the CMS nucleus 31-bit, does not
move FSCBs, PLISTs or DIAG plists, and does not touch the 156 strips or 34
ICM-3 sites in nucleus code that never sees a high address. Those are the
full-conversion items (a 31-bit CMS proper), recorded as **M6, deferred** in
`18-TRACEABILITY.md`, and are not on the road to 18 MB.

## M5b worklist (measured from source/cms)

**Old-PSW decoding** — in EC mode the ILC and code are at the fixed
locations, not in the PSW:

| Module | Sites | What they read | EC-mode source |
|---|---|---|---|
| DMSITS | `CLI SVCOPSW+3,201/202/203` (00268000, 00328000, 00330000, 00850000, 01067000), `IC XR,SVCOPSW+3` (00749000), `TM SVCOPSW+4,X'80'` ILC (00706000) | SVC number, ILC | X'8B' (code), X'89' (ILC) |
| DMSITE | `CLI EXTOPSW+3,X'80'` (00084000), `CLC EXTOPSW+2(2),=X'4001'` (00196150), `STH/CH IOOPSW+2` (00199000, 00231000) | external code, I/O device | X'86', X'BA' |
| DMSITP | `IC WORDP,OPSW+3` (00129000), `IC R10,OPSW+4` + `OPSW+3` (00142050/00142200), `IC XR,OPSW+3` (00152000) | program code, ILC | X'8F', X'8D' |
| DMSIOW | `MVC IOOPSW+2(2),SAVIOLD+2` (00162000) | device address | X'BA' |
| DMSINI | `LH R13,IOOPSW+2` (00275000) | device address | X'BA' |

`L Rx,SVCOPSW+4` as a return address (7 sites) keeps working: in AMODE 24
the hardware ignores byte 0 of a branch address, and bit 32 is what a 31-bit
caller wants kept (M5d).

**PSW constants** (BC `channels‖key AMWP` → EC `00000011‖key 1MWP`):
`NEWPSWS` and `NIOPSW/WAITPSW/WAKEPSW` in DMSINI and DMSINS (`AL2(MCKM,0)` →
`X'0008'`-style with the EC bit), `WAITNG X'FF060000'` DMSIOW, `ECBPSW`
DMSSVN, `DIE` DMSFNS, `WAITPSW` DMSABN, `=AL1(0,MCKM,0,202)` DMSITS
00249000 (the simulated SVC old PSW), DMSITS `ITSPSW`/`RET`. `COMPWORK
X'00020000'` in DMSARX/DMSASM is a size, not a PSW. The guest needs
`ECMODE` in its directory entry (MAINT, CMSUSER, CMSBATCH) — CP's DMKPRV
rejects an EC PSW otherwise.

## M5b as built (6 October)

XA0051DK, one deck for 30 CMS modules (ECMODS in `updates/build.py`): the
PSW constants, the 16 decode sites, 133 SSM masks, and three things the
worklist did not have, each found by booting:

1. **The startup PSWs DMSITS builds** for every routine it dispatches —
   `ITSPSW`/`RET` at location 0 — were constructed from scratch as BC PSWs
   (`FF E0` for a user routine, `00 00` for a system one). So the first EC
   nucleus IPLed, ran DMSINI in EC mode, and then every CMS routine ran in
   BC mode again and CP stored BC-format old PSWs (`DMSSVT121S UNSUPPORTED
   SVC 202`). They are now `03 0C` / `00 0C`; the short-path test is
   `CLC ITSPSW(2),=X'000C'`; `DMSEXS` and the BREXX entry PSW likewise.
   The save-area copy of the SVC old PSW (`OLDPSW`) carries the SVC code from
   X'8A' in bytes 2–3, so DMSSVT, DMSDOS and DMSSLN — which read `OLDPSW+3`
   — are untouched; the two places that turn it back into a return PSW clear
   those bytes first (an EC PSW with bits 24–31 set is a specification
   exception).
2. **The IPL device address.** In EC mode a S/370 IPL leaves it at X'BA',
   not in `IPLPSW+2`; DMSINI reads X'BA'. CP's side of that was I-241: the
   I-47 card had turned DMKVMI's `STH R13,INTTIO` into `SYSIPLDV`, not
   seeing that DMKVMI runs *inside the guest* (DMKCFG pages it into the
   virtual machine's X'20000'), so that low core is the guest's. Found with
   `IPL 290 STOP` and `D 0.C0` before DMSINI's first instruction.
3. **Wait PSWs with EBCDIC in the address** (`RDERRPSW CL4' INI'`,
   DMSCRD's `CL4'CON1'`): bit 32 on is a specification exception in EC mode,
   which turned "wait for the operator" into a restart loop. Byte 4 is
   zero now, three letters remain.
4. **A reader IPL arrives in BC mode** — the card loader branches to DMSINI
   under its own PSW — while a disk IPL loads the EC IPL PSW. DMSINI now
   `LPSW`s itself into EC mode at entry, so `cmswrite`'s `IPL 00C` and the
   later `IPL 290` behave the same.

The guest needs `SET ECMODE ON` (the directory `ECMODE` option follows);
`cmswrite` issues it after VMFLOAD (it resets the VM). CP's EC reflection
needed nothing: `TRACE SVC` on the EC nucleus shows `X'88' = 000200CA`, old
PSW `000C0000 00020294`, new PSW → DMSITS, for every SVC.

**Diagnostics that paid for themselves:** CP's own `TRACE PROG` / `TRACE
SVC` stop the virtual machine at each event and leave the terminal in CP
mode, so `D G`, `D PSW`, `D 0.C0` from the test script show the guest's
exact state — cheaper and better aimed than a Hercules instruction trace,
which sees real addresses only.

5. **Startup PSW addresses carry flag bytes.** A nucleus extension's
   `SCBPSW+4` (DMSREX: X'20') and NUCBREXX are copied into PSW bytes 4–7;
   BC ignored byte 4 (ILC/CC), EC demands it zero. DMSITS (NUCX and START
   paths) and DMSEXC clear it.
6. **Command modules** (TYPE, LISTFILE, COMPARE, SYNONYM, TAPE, AMSERV,
   FORMAT, RENAME, VMFPLC2): `cmsstage DMSxxx:XA0051DK`, `CMSGEND cmd`,
   copied to 290 as mode 2.
7. **Third-party code** (I-242): GCCLIB/BREXX hard-code `SSM =X'FF'`; fixed
   to save/restore the real mask, which needs ECMODE in the directory for
   BC machines too (I-243) — now set for every logon-able user.

**Done 6 October 05:58 (w190, w192):** the same CMSUSER IPLs 190 (BC,
`FF06…`) and 290 (EC, `030E…`), the PROFILE EXEC runs under BREXX, and
`REXXTRY` works in both. Test: `tests/runs/ecmode-bc-ec.json`.

**Not converted (known):** DMSDBG's `PSW1` (the DEBUG command's PSW
constant); DMSLFN (RXLOCFN, built outside CMSGEND); the 290 nucleus is the
test system — moving it to 190 is a release decision.

## M5c as built (6 October)

**HIGHSTOR**, a nucleus extension (`arch/31bit/cms/HIGHSTOR.ASSEMBLE`),
instead of a fifth DMSFRE region. DMSFRE is 24-bit through and through:
its free chains live inside the free blocks, its masks are X'00FFF000',
and its sizes are capped at X'00FF0000', so a high region inside it means
every chain walk in AMODE 31 -- a rewrite. HIGHSTOR keeps a page bitmap
**below** the line (64 KB covers 2 GB) and never touches a high page
itself, so it runs AMODE 24, except for the 31-bit SSK that gives each page
it hands out the user key (E). CMS proper never sees the region, which is
the XA-CMS-light rule.

    PLIST  CL8'HIGHSTOR',CL8'OBTAIN',F'bytes',A(0)   -> address, R15=0
           CL8'HIGHSTOR',CL8'RELEASE',F'bytes',A(address)
           HIGHSTOR QUERY | RESET                   (also as commands)
    RC     0 ok, 1 no storage, 4 bad size, 6 bad release, 8 bad function

Loaded with `NUCXTEXT HIGHSTOR (SYSTEM PERM`; runs in key 0 (IPK/SPKA, as
GCCLIB does) because its data is nucleus-key.

**CP side (I-244):** native BSM was invisible to CP's VMAM31, so the SSK
on a high page would have been simulated with a 24-bit address. DMKPRG now
takes the mode from every intercepted PSW.

**Observable met (w202, `tests/runs/highstor-64m.json`):** in a 64 MB
EC-mode CMS, `HIGHSTOR 16384K-65536K TOTAL 49152K FREE 49152K`; HSTEST
(`arch/31bit/cms/HSTEST.ASSEMBLE`, user key) obtains 40 MB at X'01000000',
switches to AMODE 31 with BSM, writes and reads back every page, returns to
AMODE 24 and releases it: `HSTEST OK`. 1.34 s CPU including ~20,000
simulated SSKs.

**Open for M5c:** load HIGHSTOR at IPL (SYSPROFX), and give back a program's
pages when it abends (today `HIGHSTOR RESET` does it by hand).

## M5d as found (6 October): the compiler already knows how

No GCCLIB port is needed to run the **compiler** above the line. CE's GCC
EXEC runs `CHECK380` and picks **GCC380 MODULE** on S/380, GCC370 otherwise.
GCC380 is GCC linked with PDPCLIB built `SYS=S380`: it switches itself to
AMODE 31 (`@@SETM31`, BSM), drops to AMODE 24 around every CMS call
(`@@SVC202`, OPEN/GET/PUT), and takes its heap with `GETMAIN RU,LOC=ANY`
-- SVC 120 -- in one 60 MB piece. That is how the SixPack compiled GCC
itself (">16 MB for the compiler"), but only on S/380 Hercules, which backed
CE's placeholder SVC 120 (a fixed X'04100000').

On VM/370plus the pieces are now real: EC-mode CMS (M5b), HIGHSTOR (M5c), the
native-BSM fix in CP (I-244) and DMSSVT's SVC 120 (I-245). **W209: in a
128 MB EC-mode CMS, `GCC31 HELLO31` (GCC EXEC forced to GCC380) compiled and
assembled a C program with its 60 MB heap at X'01000000', and the program
ran: `hello from VM/370plus, compiled by GCC380 in AMODE 31`.** CMSUSER's
directory maximum is now 256M.

Still to do for M5d proper: C programs *built* for AMODE 31 (PDPCLIB S380
TXTLIB) and GCCLIB's page allocator (`_DMSFREE`) on HIGHSTOR -- needed for a
cREXX that runs above the line, not for compiling it.

## M5g as built (7 October): native 31-bit C, and cREXX built on the machine

M5f cross-compiled cREXX on the PC. M5g does it on VM/370plus: programs
compiled here run AMODE 31 with their heap above 16 MB.

**GCCLIB31** (`arch/31bit/gcclib31/`) is Adrian's cms-370-gcclib 1.0.0
(F0054) with the changes `mk31.py` applies by exact match:

- C runs AMODE 31. CMSENTRY enters `__cstub` by BASSM and gets back AMODE 24;
  `@@EXIT` drops to 24 first; every C function returns with `BSM 0,R14`
  (DYNSTK), so it returns in its caller's mode.
- Every CMSSYS stub that touches CMS switches to AMODE 24 on entry
  (BASR/LA/BSM, no base needed) and returns with `BSM 0,R14`: SVC 202,
  DMSFREE, FSxxxx run exactly as for a 24-bit program.
- Two heaps. `malloc` is dlmalloc with 256 KB segments from HIGHSTOR (DMSFREE
  only if HIGHSTOR is absent or full). What CMS sees -- FILE (the FSCB),
  record buffers, command strings, EPLIST argument lists, the dynamic stack
  bins (C locals go to CMS constantly) -- comes from `_lmalloc`, which is
  DMSFREE. `CMScommand`/`system()` and `CMSfunction*` copy high strings low.
- `memcpy`/`memset` loop in 16 MB - 4 KB pieces (MVCL lengths are 24 bits),
  and `string.h` sends `memcpy`/`memset`/`memcmp` to the library instead of
  GCC's inline MVCL/CLCL builtins -- a 20 MB `memcpy` moved 3 MB (w264).
- DYNSTK's `LA R11,0(,R11)` kept the stack flag byte in AMODE 31; SLL/SRL 8.
- Upstream bugs fixed on the way: stack bins for frames over 16 KB were sized
  with `&&` (logical AND), and `%g` kept trailing zeros.

`GCLB31 EXEC` builds it on the machine (assembler stubs with ASSEMBLE, C with
GCC370, the CSECT named `$fn` with EDIT -- TXTLIB refuses private code and
`TIME`/`MALLOC`/`SIGNAL` clash with the functions). `M5G2` proves it: 30 MB at
X'01000340', a 20 MB `memcpy`, 20,000 small blocks, 20 KB frames, file I/O
and `system()` from buffers above the line, `exit(3)`, HIGHSTOR all returned.

**I-252** (DMSSMN XA0051DK): GCC380 abended 80A after its output on larger
sources. Its PDPCLIB FREEPOOLs a buffer pool whose BUFCB it never set; the
stale pointer above 16 MB made CMS read the FREEMAIN as a GETMAIN (byte 0 of
R1 nonzero). From AMODE 31, SVC 10 now follows the XA rule.

**cREXX.** `CRXMK31 EXEC` compiles the 2022 tree with GCC380, GCCLIB31's
headers and macros, and links `RXCN RXASN RXBVMN RXDASN` (about 90 s CPU).
The native RXC's DLMALLOC PANIC was cREXX's own: `cms.h` mapped
`snprintf`/`vsnprintf` to `sprintf`, which ignores the size, and the compiler
sizes its buffers by calling `vsnprintf` with a small one first. A real
bounded version fixes it. (LOAD also took the 24-bit build's TEXT decks from
D first; D is released while linking.) w265: RXCN BASIC -> RXASN -> RXBVMN,
and the w259 test set, give the cross-built output line for line except
`é` shown as a blank on the console. Regression: `tests/runs/m5g-native.json`.
