# Installing this in your own environment

Asked on 3 October and owed since: *"how can I install the current version in my
environment?"*

The honest headline first, because it decides whether the rest is worth your
afternoon: **what this repository distributes is a set of update decks and a
generator, not a system image.** You do not install VM/370+; you rebuild it from
a pristine VM/370 CE distribution plus our decks. And as of this writing the
result IPLs, initialises, prints its banner, accepts `cold`, auto-logs on
OPERATOR and reports its storage sizes — and then does not yet take console
input, because of wall 20 (`I-183`/`I-184`). So the procedure below is
reproducible and the artifact is real, but it is a development checkpoint, not
something to run work on.

## What you need

| | |
|---|---|
| A pristine **VM/370 Community Edition V1 R1.2** distribution | the zip; do not point any of this at a pack you care about |
| **Hercules 3.13** | the build machine. Every measurement this project has made is against it |
| **Hercules 4.9.1** (optional) | a second opinion on architectural fidelity, never a replacement — see `claude/HERCULES-4.md` |
| **Python 3** | the generator and every tool |
| about **16 GB** of disk and an hour of wall clock for a full build | |

Nothing else. There is no cross-assembler in the loop: every module is
assembled by **CMS's own assembler, under CP, on the pack** — which is the point,
and why the build takes an hour rather than a minute.

## The shape of it

```
pristine CE pack                      (CE's own CP, S/370, boots normally)
   + 55 update decks + 47 AUXLCLs     (generated by updates/build.py)
   → VMFMAC DMKLCL                    (our macros join CE's maclib)
   → VMFASM each patched module       (under CE's CP, in S/370 mode)
   → VMFLOAD CPLOAD DMKLCL            (punch the nucleus)
   → CP IPL 00C                        (the standalone loader writes it to 6A1)
   → switch Hercules to ESA/390
   → IPL 6A1                           (the converted CP)
```

Two things about that sequence are worth stating plainly, because both cost this
project a day when they were assumed rather than checked.

**The build runs in S/370 and the test runs in ESA/390.** CE's own CP does the
assembling, and CE's own CP is a System/370 program; it dies instantly in
ESA/390 mode. Our converted nucleus is the opposite. A run in the wrong
architecture does not fail loudly — the instruction trace simply comes back
empty, which reads exactly like "this code never executes". `build.sh` verifies
the architecture **from the log** at every step rather than trusting the config
file (`I-115`).

**The nucleus is written by IPLing the standalone loader, not by copying a
file.** `VMFLOAD` punches a load deck; `CP IPL 00C` reads it and writes cylinder
0 of 6A1. If that step is skipped, every later test measures the *previous*
nucleus and does so convincingly.

## The procedure

```bash
# 1. Lay out a disposable extraction.  Keep the distribution zip pristine.
unzip VM370CE_V1_R1_2.zip -d /somewhere/scratch
export CE=/somewhere/scratch/VM370CE.V1.R1.2
export REPO=/path/to/this/repository

# 2. Generate the decks.  Validates as it goes and refuses to emit a bad one.
python3 $REPO/arch/31bit/updates/build.py

# 3. Check them.  Both of these are cheap and both have caught real defects.
python3 $REPO/arch/31bit/tools/replchk.py   # four invariants on every deck
python3 $REPO/arch/31bit/tools/symchk.py    # no symbol collisions

# 4. The full build: stage 104 files, VMFMAC, assemble 186 modules.  ~70 min.
$REPO/arch/31bit/tools/build.sh full SNAP-BASE

# 5. Write the nucleus.
$REPO/arch/31bit/tools/build.sh write

# 6. IPL it in ESA/390 and watch.
$REPO/arch/31bit/tools/build.sh test
```

`build.sh full` ends by taking a snapshot named `SNAP-HHMM`. After that, a
one-module change is

```bash
$REPO/arch/31bit/tools/build.sh spec SNAP-HHMM DMKPGS:XA0036DK
$REPO/arch/31bit/tools/build.sh write
$REPO/arch/31bit/tools/build.sh test
```

which is four minutes instead of seventy. **A snapshot starts invalid and
becomes valid only when a condition observable in the log is met** — Mike's
framing, 1 October, and `snapshot.py` enforces it. It refuses a stale snapshot
and names every input that changed since it was taken, because restoring a
snapshot and reassembling one module on the reasoning that "the MACLIB is
unchanged" produced a nucleus from one hour carrying a module from another, and
it reproduced an *older* failure convincingly enough to be read as a new one
(`I-111`).

## Things that will bite you

**Always `/cp shutdown` and then Hercules `exit`.** Killing Hercules leaves the
warm-start area inconsistent, and the next IPL's behaviour is then a measurement
of the kill, not of the code (`I-38`).

**Never run two Hercules instances on one pack.** Both will IPL and both will
write. `build.sh` guards against it, and the guard exists because it happened
(`I-63`). Note that `pgrep -c hercules` returns **0** while Hercules 4.9.1 is
running — 4.9.1 renames its main thread `impl_thread` — so any wait loop built
on that is a wait loop that always succeeds (`I-180`).

**A line typed at a 3215 with no outstanding read is discarded** with no error
and no trace. So a `cold` that arrives unanswered proves nothing on its own, and
"CP ignored my command" is not a finding until you know a read was outstanding.

**Above 16 MB you are measuring Hercules, not CP.** CE generates
`SYSCOR RMSIZE=16384K`, and DMKCPI takes the smaller of the real machine and the
SYSGEN size, so a 32 MB run has the same CP storage, the same geometry and some
unused real storage. Genuinely testing larger machines needs `RMSIZE`
regenerated — and, separately, `I-185`.

## What you get

A CP that, in ESA/390 mode on either engine:

- IPLs from 6A1 and sizes storage
- resolves SYSRES and reads the directory
- passes CE's own System/380 probe
- prints `VM/370+ Community Edition Version 1 Release 1.2`
- reaches `Start ((Warm|Force|COLD|CKPT) ...)` and accepts `cold`
- auto-logs on OPERATOR and prints
  `DMKCPI957I Storage size = 16384 K, Nucleus = 348 K, Dynamic Paging = 14776 K, Trace Table = 240 K, Free Storage = 1020 K`
- starts the monitor

and then does not accept a typed command, for the reason recorded in
`I-183`/`I-184`. Hercules 3.13 reaches the prompt in about 200 seconds; 4.9.1 in
about 16. They agree on everything that has been compared.

`CMS` does not run yet, so there is nothing to log on to and do work in. When
that changes this document gets a section on it rather than a promise here.
