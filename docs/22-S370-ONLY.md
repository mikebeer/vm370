# The S/370-only instruction inventory

`STIDC` in `DMKIOG` was found by reading one module for a different reason.
That is not a method, and the failure mode it exposed is the worst kind this
project has: **an S/370-only instruction assembles perfectly.** Assembler XF
does not know which architecture the object will run on, so `NO STATEMENTS
FLAGGED` says nothing about it. The module is clean, the nucleus builds, and
the CPU takes an operation exception the first time the path executes.

The 173-module nucleus cannot be read line by line, so the sweep is mechanical:
`tools/s370only.py` reads Hercules's own opcode table, where a row marked
`GENx370x___x___` is installed in S/370 mode and in no other.

    python3 tools/s370only.py <hercules>/opcode.c /home/claude/vmce [--all]

## Result

| Mnemonic | Opcode | Nucleus sites | Other | Family | Becomes |
|---|---|---|---|---|---|
| `TIO` | `9D` | 71 | 20 | channel | `TSCH`, condition code inverted |
| `SIO` | `9C` | 48 | 13 | channel | `SSCH` |
| `ISK` | `09` | 38 | — | key | `ISKE` |
| `SSK` | `08` | 16 | — | key | `SSKE` |
| `RRB` | `B213` | 13 | — | key | `RRBE` |
| `HIO` | `9E` | 5 | — | channel | `HSCH` |
| `HDV` | `9E01` | 4 | — | channel | `HSCH` |
| `TCH` | `9F` | 3 | — | channel | none — force the available path |
| `CLRIO` | `9D01` | 1 | — | channel | `CSCH` |
| `STIDC` | `B203` | 1 | — | channel | none — report every channel unidentified |

**200 nucleus sites across 28 modules.** The 33 non-nucleus sites are in
`DMKDDR`, `DMKDIR`, `DMKFMT` and `DMKSSP` — standalone utilities that run
outside CP and are out of scope until someone wants them.

## Two families, and they are not equally hard

**The storage-key family — 67 sites — is mechanical.** `ISKE`, `SSKE`, `RRBE`
and `IVSK` are all `GENx370x390x900`: valid in S/370, ESA/390 and
z/Architecture alike. So each substitution is safe in *both* directions and can
be made before anything else changes, on a system that still runs S/370.
Operand order differs (`ISKE R1,R2` is RRE against `ISK`'s RR) and `SSKE` is
`RRF_c`, so it is not a textual rename, but it is a local, testable edit per
site with no control-flow consequence. The 4 KB-key work in `R-12` overlaps
this heavily and `I-29` shows CE already has prior art in six of its own decks.

**The channel family — 133 sites — is not mechanical, and 28 modules is the
number that matters.** Two reasons:

1. **The condition codes invert.** `cc1` from `TIO` means "CSW stored"; `cc1`
   from `TSCH` means "no status pending". A site that branches on `cc1` to
   handle a completed operation must branch on `cc1` to handle a *free device*
   instead. There is no substitution that preserves the sense, so every site
   is a small piece of reasoning, which is exactly what `R-01` and `R-02` are
   about.
2. **It is not confined to `DMKIOS`.** The plan up to now has treated channel
   I/O as DMKIOS's business. It is not: `DMKCKP`, `DMKDMP`, `DMKCNS`,
   `DMKCPI` and `DMKPSA` all issue `SIO`/`TIO`/`HIO` directly, because
   checkpoint, dump, console and initialisation do their own I/O without the
   scheduler. Those are precisely the paths M3a needs in order to IPL and
   shut down.

## What this changes

The milestone set said M1 was "DMKIOS plus the eight modules the PSA rename
broke". The rename was never the real measure of the work — it was the measure
of what *fails to assemble*, which is the subset the assembler happens to
catch. The instruction inventory is the real one, it is an order of magnitude
larger, and none of it announces itself at build time.

Concretely:

* M1 should end with the storage-key family done, because it is safe on S/370
  and removes 67 sites from the ESA/390 risk surface at zero architectural
  cost.
* M3a cannot be reached by converting `DMKIOS` alone. `DMKCPI` (IPL),
  `DMKCKP` (checkpoint) and `DMKPSA` must be converted for CP to start and
  stop, and they are already on the broken list for unrelated reasons —
  `DMKCKP` and `DMKDMP` for their `INTTIO` sites. Those should be done in one
  pass per module, not two.
* `DMKBTS` has no source at all (`I-35`), so if its object deck issues any of
  these it cannot be fixed. `R-24` covers reading its ESD and RLD records to
  find out, which should happen before M3a rather than after the first IPL.

## Caveat

Counts are sites in the resolved tree as imported on 20 September 2026
(`UPSTREAM.md`), which `R-23` now rates low-risk: run20 independently confirmed
the tree against CE's own build, flagging exactly the `IOELPNTR ×2` and
`CHANID ×3, ECSWLOG ×2, IOELPNTR ×1` the static scan predicted. The opcode-column
parser is a heuristic — `AMBIGUOUS` in the tool lists the mnemonics that are
also CP labels, and `FREE`/`FRET` are real DMKFRE entry points — but none of
the ten mnemonics above is in that set.

`HDV`, `SIOF`, `CLRIO`, `CLRCH` and `TIOB` are **not** rows in Hercules's opcode
table: they are sub-functions of `9C`/`9D`/`9E`/`9F` dispatched on the
low-order bits of the operand address. A purely table-driven sweep misses all
five, and `HDV` alone accounts for four nucleus sites — two of them the ones
`DMKIOS` still owes. They are supplied by hand in `SUPPLEMENT`. If any further
S/370 mnemonic is dispatched the same way, this sweep misses it too.

## Where the channel sites actually are

The per-module breakdown is the part that changes the plan, and it is not what
the milestone set assumed:

| Module | Sites | Role | Mnemonics |
|---|---|---|---|
| `DMKCKP` | 25 | checkpoint / shutdown | `TIO`×13 `SIO`×10 `HIO`×2 |
| `DMKDMP` | 22 | abend dump writer | `TIO`×14 `SIO`×8 |
| `DMKCPI` | 21 | CP initialisation, runs at IPL | `TIO`×13 `SIO`×7 `HIO`×1 |
| `DMKLD00E` | 19 | the CP nucleus loader | `TIO`×11 `SIO`×8 |
| `DMKSAV` | 11 | saved-system reader/writer | `SIO`×6 `TIO`×5 |
| `DMKIOS` | 10 | the I/O scheduler itself | `TIO`×4 `SIO`×2 `HDV`×2 `TCH`×2 |
| `DMKVMI` | 7 | VM initialisation | `TIO`×4 `SIO`×3 |
| `DMKCNS` | 5 | operator console | `HDV` `TIO` `SIO` `HIO` `CLRIO` |
| `DMKIOT` | 5 | I/O interrupt entry | `TIO`×3 `SIO`×2 |
| `DMKOPR` | 3 | operator commands | `TIO`×2 `SIO`×1 |
| `DMKPSA` | 2 | prefix save area / restart | `HIO`×1 `TIO`×1 |
| `DMKENT` `DMKIOG` `DMKVSJ` | 1 each | NCP, CCH init, spool journal | `TCH`, `STIDC`, `HDV` |

**`DMKIOS` is 10 of 133 sites — under 8%.** The scheduler was treated as the
centre of the channel work and it is not. The five largest users are the
*standalone* I/O drivers: the loader, the saved-system reader, IPL
initialisation, checkpoint and the dump writer. They bypass `DMKIOS` entirely
and poll the channel themselves, because they run before the scheduler exists
or after it has stopped:

    DMKLD00E   TIO   0(2)    CLEAR THE PATH
               SIO   0(2)    DO THE INITIALIZE PRINTER
               TIO   0(2)    WAIT TILL THE INTERRUPT CLEARS

## What "the channels are done" would require

Three stages, in dependency order:

1. **Assembles** — after `DMKCCH`, every nucleus module assembles. This is the
   only stage the PSA rename ever measured, and it is worth nothing on its own:
   `STIDC` proved that a clean assembly and a working instruction are unrelated.
2. **IPLs and stops** — the bootstrap chain, 58 sites in four modules:
   `DMKLD00E` (19) + `DMKSAV` (11) + `DMKVMI` (7) + `DMKCPI` (21), plus
   `DMKCKP` (25) to shut down cleanly. `DMKDMP` (22) belongs here too, not
   later: without it a failure during M3a produces no dump, which is the one
   diagnostic that matters when CP dies during initialisation.
3. **Runs guest I/O** — `DMKIOS` (10 outstanding) and `DMKIOT` (5, plus the
   interrupt entry and CR6), and `DMKCPI`'s subchannel-discovery loop filling
   `RDEVSSID` via `STSCH`/`PMCWDEV`.

Stage 2 is the bulk and it is all on M3a's critical path. Stage 3 is what M1
step 4 and step 5 were already about.

Two things stay open past all three. `R-03` is stubbed, not implemented: channel
errors terminate the system instead of being analysed, and real ESW/ECW handling
is M4-or-later work. And `R-24` is unknown rather than open — `DMKBTS` may issue
channel I/O and has no source.

## The DC-encoded sites, all six closed

`dc_sites()` finds six hand-assembled channel instructions, because Assembler XF
has no mnemonic for `CONCS`, `DISCS` or `CLRCH` and the original authors wrote
the bytes directly. **None of the six is closed by converting an instruction**,
which is the interesting part.

| Module | Bytes | Mnem | In the nucleus? | How it is closed |
|---|---|---|---|---|
| `DMKCPI` | B200 | `CONCS` | yes | dead under `AP=NO` — `XA0014DK`, `I-50` |
| `DMKVSJ` | 9F01 | `CLRCH` | yes | function removed — `XA0018DK`, `I-62` |
| `DMKCPP` | B200/B201 | `CONCS`/`DISCS` | no | `APLOAD.EXEC` only |
| `DMKMCT` | B200/B201 | `CONCS`/`DISCS` | no | `APLOAD.EXEC` only |

The four non-nucleus sites are worth a sentence because they are not a separate
piece of luck. `DMKCPP` and `DMKMCT` appear in `APLOAD.EXEC` and
`APVRLOAD.EXEC` and in **neither** `CPLOAD.EXEC` — they are attached-processor
modules in attached-processor load lists. So the one-character `AP=NO` change in
`DMKSYS` closes five of the six sites, not just `DMKCPI`'s: it makes `DMKCPI`'s
`CONCS` dead code and keeps the other four modules out of the nucleus entirely.

### Why `CLRCH` is the exception that had to be deleted

Every other S/370-only instruction in this conversion has a successor with
comparable semantics — `SIO`→`SSCH`, `TIO`→`TSCH` with the condition codes
swapped, `ISK`→`ISKE`. `CLRCH` has none, and the instruction that looks like its
successor is a trap.

`RCHP` (X'B23B') is `GENx___x390x900`: it exists in exactly the architectures
`CLRCH` does not, which is the shape of a substitution. But it resets a *channel
path*, and in ESA/390 a channel path is a shared resource the channel subsystem
owns — not something a guest can be given. VM/XA dropped dedicated channels
rather than solve this.

Three checks, each of which alone would have been enough:

* **The operand form is different.** `RCHP` takes a CHPID in R1 bits 24-31 and
  takes an operand exception if bits 0-23 are non-zero. `VCHADD` holds a channel
  address in device-number form — X'0300' for channel 3 — so `LH R1,VCHADD`
  followed by `RCHP` program-checks every time.
* **Making it assemble would make it worse.** Hercules assigns
  `chpid = devnum >> 8` (`config.c:724`), so an `SRL R1,8` would appear to work.
* **And then it would destroy the I/O configuration.** `chp_reset` calls
  `device_reset` on every device on the path, and `device_reset` is the one
  thing that clears `PMCW5_E` and the interruption parameter
  ([24-INTTIO.md](24-INTTIO.md)). CP sets both exactly once, at IPL, in
  `XA0013DK`, and has no code anywhere that re-enables a subchannel. One guest
  `CLCH` would disable every device on that channel for the rest of the IPL,
  with `SSCH` returning cc3 and no diagnostic.

So `XA0018DK` replaces the whole pass-through with `B CLCHEXIT`. `CLCH` is now
always simulated as a `TCH` — which is what `DMKVSJ` already did one instruction
earlier for every channel that was not dedicated, so the new path is one the
module has always exercised.
