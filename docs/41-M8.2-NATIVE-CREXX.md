# M8.2 — current cREXX built natively on VM/370+ (work in progress, 9 October 2026)

**Goal:** build current cREXX (adesutherland/crexx 77ba820c3) on CMS with
GCC380 and GCCLIB31. The modules are RXC82, RXAS82 and RXBVM82. They sit
beside M8.1's cross-built RXC8, RXAS8 and RXBVM8; VM/370+ ships both.

## The charset decision
GCC380 runs on an EBCDIC system and compiles string and character literals
as EBCDIC. It has no option for an ASCII execution character set. So the
native cREXX runs in EBCDIC, as IBM REXX on CMS does:
- **Scanners:** regenerated with `re2c -e`, using upstream's own
  `S370/encoding.re`. The largest one shrinks from 232,000 lines to 11,000.
- **UTF-8:** `utf.h` is replaced by a single-byte version (`m82/inc/utf.h`,
  one byte is one character, case from the C library), and `NUTF8` is
  defined.
- **Library:** it must be compiled natively too. The PC-built `LIBRARY
  RXBIN` holds UTF-8 strings and IEEE doubles; GCC380 uses hexadecimal
  floating point.

## Pipeline (`arch/31bit/m82/`)
1. `prep.py`
   - stages the 113 sources and every header they reach under 8-character
     CMS names;
   - rewrites the `#include` lines;
   - applies the native-CMS deltas (platform.c: file probe and dirent under
     `CREXX_CMS_GCC`).
2. `pre.sh`: compiles the staged tree on the PC (s390x gcc `-m31`) against
   GCCLIB31's headers, to find missing declarations and symbols.
3. `names.py`: gives the 1,109 externals that are longer than 8 characters
   (or collide when cut to 8) a short name, `CXnnnnn`. `prep.py` then
   renames them textually; macros were not enough, because cREXX `#undef`s
   some of the names.
4. `xf/xform.py`, per unit:
   - preprocesses the unit, parses it with pycparser, prunes it to the
     declarations it reaches, and works out expression types;
   - rewrites the code to get round GCC380 (next section);
   - writes one self-contained C file.
5. `mkcms.py` writes the reader deck: every unit, the table CSECTs,
   `CRX82MK EXEC`, the PARM files and `PDPTOP COPY`.
6. `mkrun.py` writes the drive.py run. In `full` mode it formats CMSUSER's
   194 as A, loads the deck and runs CRX82MK.

## Runtime layer over GCCLIB31
- **`CRXRT C`** supplies:
  - the printf family with C99 length modifiers (`%lld`, `%zu`, ...) and
    real `snprintf`;
  - `strtoll`, `strtoull`, `strdup` and the other missing string and number
    routines;
  - CMS file names: cREXX's `dir/fn.ft` becomes `FN FT M`;
  - `stat`, and `opendir`/`readdir` built on `LISTFILE * * m (EXEC`.
- **`CRXLGCC C`** supplies:
  - the 64-bit helpers GCC380 calls but nothing provides: `@@DIVDI3`,
    `@@UDIVDI`, `@@MODDI3`, `@@UMODDI`, `@@MULDI3`, `@@NEGDI2`, `@@CMPDI2`,
    `@@FIXDFDI`, `@@FIXUNS`, `@@FLOATD`;
  - `crxadd64`, `crxsub64`, `crxadt64`, `crxinc64`, `crxcmp64`, `crxucm64`
    and `crxsw64`.

  Everything in it is written with 32-bit arithmetic only.

## GCC380 defects found (each measured on CMS with small test units)
| Defect | Fix |
|---|---|
| No 64-bit add: every `long long +`, and every `- constant`, crashes the compiler with an internal error | xform turns 64-bit `+ - += -= ++ --` into helper calls |
| 64-bit compares under `&&`/`\|\|` are folded into range tests, which need an add | all 64-bit compares and truth tests become calls |
| "Unable to generate reloads" for the DImode compare-and-branch in large functions | same as the row above |
| `SLDA` used for 64-bit `<<` (keeps the sign bit) | `SLDA OPSYN SLDL` as the first statement of PDPTOP COPY (CRX82 MACLIB) |
| 64-bit libcalls made through `=A(@@...)` without EXTRN, which does not assemble | EXTRN for them in PDPTOP COPY |
| unsigned 64-bit to double: small odd values come out wrong | open; not used by cREXX as far as we know |

## Assembler and CMS limits found
| Limit | Fix |
|---|---|
| A CMS file holds 65,533 records | a unit is split into parts: statics become externals `CYnnnnn`, and each part defines some of the functions and declares the rest |
| About 400 ESD entries per assembly (IFO264, "too many ESD entries") | parts are cut on a budget of 330 external symbols |
| The VM's run() calls about 680 outlined handlers by itself | it calls them through a table that each part fills in once |
| Lemon parser tables of 68,000 entries (one DC line per element) | the tables become assembler CSECTs `CTnnnnn`, with `DC X'..'` lines of 26 bytes each |
| `CREXX_VM_HANDLER_PANEL` 20 inlines the handlers into run() | the native build sets 1, so the handlers are out of line |
| GCCLIB31 stdio handles at most 32,768 records per file | the ASMFIX filter idea was dropped; PDPTOP does its job |

## More GCC380 defects (9-10 October)
| Defect | Fix |
|---|---|
| A 32-bit constant expression widened to 64 bits (`(uint64_t)sizeof x`, enum values) lands in the high half | xform widens them at run time (`crxs64`/`crxz64`) |
| Small 64-bit literals with suffixes (`7ULL`, `UINT64_C(0x7F)`) and folded ones (`~0ULL`): the same MVC 8 from a 4-byte literal | xform folds literal expressions in 64-bit arithmetic and uses `crxkN` statics; also for `& \| ^` with 64-bit operands |
| `x & (unsigned char)(1 << n)` tested for non-zero: a wrong bit test (the RXBIN LZSS decoder) | the shift goes through `crxid32()` |
| Inlined functions with 64-bit parameters get an argument as 0 (the VM's `rxinteger_checked_add`) | no inlining in the native build (`inline` defined away) |

## Test aids
- `prep.py` with `M82TRACE=file.c` marks every `return 0`/`goto error` of a staged
  file; RXBVM82 prints the last 16 on a load error.
- `xf/pcfix.py` makes an xform output unit build for s390x Linux (real varargs,
  C library stdio for GCCLIB's CRAB). The transformed RXBVM82 then runs under
  `qemu-s390x` on the PC: when that copy is right and the CMS one is not, the
  fault is GCC380's code generation, not xform.
- Decoding a CMS-written RXBIN on the PC and comparing it with the PC's own
  found the varint writer bug.
